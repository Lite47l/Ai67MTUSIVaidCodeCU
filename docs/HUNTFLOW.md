# Хантфлоу

Реализован клиент API v2 по [официальной документации](https://api.huntflow.ru/v2/docs) и [OpenAPI](https://api.huntflow.ru/v2/openapi.json).

## Настройка

1. В Хантфлоу откройте **Настройки → API → Добавить токен**. Возьмите `access_token` с доступом к нужной организации, чтению кандидатов/истории и добавлению комментариев.
2. Заполните корневой `.env`:

```dotenv
HUNTFLOW_BASE_URL=https://api.huntflow.ru/v2
HUNTFLOW_ACCESS_TOKEN=ваш_access_token
HUNTFLOW_ACCOUNT_ID=123
```

`HUNTFLOW_ACCOUNT_ID` — ID организации, не пользователя. Его можно узнать через `GET /accounts`:

```powershell
$HuntflowToken = Read-Host 'Access token Хантфлоу'
Invoke-RestMethod -Uri 'https://api.huntflow.ru/v2/accounts' -Headers @{Authorization = "Bearer $HuntflowToken"} | Select-Object -ExpandProperty items
Remove-Variable HuntflowToken
```

Для sandbox или другого региона укажите API base URL, выданный Хантфлоу, с окончанием `/v2`. Удалённый адрес должен использовать HTTPS; HTTP разрешён только на loopback для локальных тестов.

3. Запустите Docker Desktop, затем из папки проекта:

```powershell
docker compose up --build -d
```

Откройте HR → **Хантфлоу**. Название организации означает успешную проверку токена. Токен хранится только в окружении Go и не передаётся браузеру, Qwen или Python-агенту.

## Участники

В разделе **Хантфлоу** укажите ID кандидата, подразделение и ID наставника. Для существующего участника укажите его ID, например `СТ-004`. Для нового можно оставить поле пустым: получится `HF-<ID кандидата>`.

Приложение проверяет кандидата в заданной организации и атомарно создаёт карточку/привязку. ФИО, контакты, резюме и вся база кандидатов не копируются. Существующие подразделение, наставник и связь с другим кандидатом не перезаписываются. Один кандидат соответствует одному стажёру. Повтор такой же привязки допустим. Учётные записи создаются прежним способом; ручное добавление HR и автоматическая регистрация из анкет сохраняются.

## Рекомендации

Откройте профиль → **История и оценки**, выберите месяц. В рекомендации нажмите **Подтвердить запись в Хантфлоу**. Перед кнопкой показаны организация и ID кандидата.

Передаётся нейтральная рекомендация, месяц, ID стажёра и получатель HR/наставник. Частные комментарии анкеты, оценки и свободный пересказ модели не отправляются. После успеха показывается ID записи Хантфлоу.

API создаёт **комментарий в личных заметках кандидата**: `POST /accounts/{account_id}/applicants/{applicant_id}/logs` с полем `comment`, без `vacancy`. Это запись для работы HR; она не назначает задачу пользователю Хантфлоу, не меняет этап найма, не отправляет письмо и не создаёт событие календаря. Доступ к заметкам определяется настройками Хантфлоу. Существующий универсальный HR-коннектор работает независимо.

## Доставка и ограничения

Подтверждение, исходный получатель и статус сохраняются в SQLite. После успешного ответа повторная отправка не выполняется. Если ответ потерян, перед повтором проверяется история личных заметок по стабильному маркеру `[mgts-pulse:…]` с учётом пагинации. При ошибке чтения истории запись не отправляется. Более 100 страниц требуют ручной проверки. Один процесс Go и lease защищают от параллельного подтверждения.

У API комментариев нет документированной гарантии `Idempotency-Key`: проверка маркера уменьшает риск дубля, но не даёт абсолютной гарантии при задержке видимости записей или их ручном удалении/редактировании. При сомнении HR должен проверить заметки кандидата перед повтором.

Автоматического обновления токенов нет. По документации access token действует 7 дней. При 401 обновите пару токенов в Хантфлоу либо через `POST /token/refresh`, замените `HUNTFLOW_ACCESS_TOKEN` в `.env` и повторите `docker compose up --build -d`. Refresh token в приложение не передаётся. 403 означает отсутствие доступа, 429 — ограничение частоты; приложение показывает понятную ошибку без тела ответа сервиса.

## API приложения

Все три ручки доступны только HR с действующей сессией:

- `GET /api/v1/hr/integrations/huntflow` — проверить организацию.
- `POST /api/v1/hr/integrations/huntflow/participants` — тело `{ "applicantId": 42, "internId": "СТ-004", "department": "HR-блок", "mentorId": "Н-004" }`.
- `POST /api/v1/hr/interns/{id}/recommendations/{recommendation}/huntflow?month=4` — подтвердить запись рекомендации; 200 — записана, 202 — отправляется, 502 — ошибка доставки, 422 — нет подходящей привязки.

В профиле HR добавлены `huntflow`, `huntflowConfigured` и `recommendations[].huntflowDelivery`. Наставнику и стажёру привязка и доставка не выдаются.

## Проверка

```powershell
go test ./internal/pulse -run Huntflow -v
go test ./... -count=1
go vet ./...
```

Тесты используют локальный HTTP-сервис: проверяют Bearer, пути API v2, импорт и конфликт привязки, роли, пагинацию, потерю ответа после записи и безопасные ошибки. Реальные кандидаты не меняются. Для проверки в вашем аккаунте используйте тестового кандидата: свяжите его, подтвердите одну рекомендацию и проверьте личные заметки. Точное повторное подтверждение должно вернуть прежний ID записи.
