## 1. Скрытый сигнал: «оценки молчат, текст говорит»

**Боль:** стажёр ставит 4, чтобы не выглядеть жалобщиком, а настоящее пишет в комментарии. Правило по числам такой случай пропускает.

**Правило:** в одном ответе есть негативная тема комментария **и** связанный с ней показатель ≥ 4 → сигнал `kind: "text_score_mismatch"`, `status: "attention"`. В `evidence` два элемента: оценка (`field`, `value`) и цитата (`quote`).

**Темы и поля (по CONTRACTS.md):**

| Тема | Стажёр | Наставник |
|---|---|---|
| `feedback` (обратная связь, ожидание ответа, редкие встречи) | `mentor_support` | `mentor_team_interaction` |
| `clarity` (непонятные задачи, приоритеты) | `task_clarity` | `task_understanding` |
| `workload` (нагрузка, параллельные задачи) | `workload_comfort` | `deadline_organization` |
| `planning` (планирование, сроки) | `workload_comfort` | `deadline_organization` |
| `team` | `team_interaction` | `mentor_team_interaction` |
| `growth` (хочу сложнее или самостоятельнее) | **не сигнал**, метка «запрос на рост» | то же |

`growth` — не жалоба. Если пометить «хочу задачи сложнее» как проблему, система покрасит лучших стажёров. Для HR это скорее аргумент в пользу оффера.

**Главный пример: СТ-004, период 3.**
- Стажёр: оценки 4–5, `workload_comfort` = 4; «Стало больше параллельных задач», «Нужно внимательнее планировать загрузку».
- Наставник: все оценки 5; «Стоит продолжать следить за нагрузкой».
- Период 4: `workload_comfort` = 2 (critical), сроки перенесены.
- **Числовое правило срабатывает в периоде 4, скрытый сигнал с обеих сторон виден уже в периоде 3.**

**Тест-кейсы для `tests/analysis/`:**

| Должен сработать | Оценка | Цитата |
|---|---|---|
| СТ-004, п.3, intern, `workload` | `workload_comfort` 4 | «Стало больше параллельных задач.» |
| Н-004 → СТ-004, п.3, mentor, `workload` | `deadline_organization` 5 | «Стоит продолжать следить за нагрузкой.» |
| СТ-001, п.1, intern, `feedback` | `mentor_support` 4 | «Нужно быстрее получать обратную связь по промежуточным результатам.» |
| СТ-001, п.2, intern, `feedback` | `mentor_support` 4 | «Иногда не хватает короткой сверки с наставником по новым задачам.» |
| СТ-002, п.4, intern, `workload` | `workload_comfort` 4 | «Иногда нагрузка выше комфортной.» |
| Н-004 → СТ-004, п.4, mentor, `workload` | `deadline_organization` 4 | «…часть сроков пришлось перенести.» |

| Не должен сработать | Почему |
|---|---|
| СТ-001 п.4 «Хотелось бы больше задач повышенной сложности.» | `growth` |
| СТ-002 п.6 «Хотелось бы больше ответственных задач.» | `growth` |
| СТ-001 п.5–6 «Сложностей за период не было.» | отрицание |
| СТ-004 п.4 «…по задачам и взаимодействию проблем нет.» | отрицание (часть про нагрузку остаётся) |

Допустимо, но не обязательно: СТ-005 п.4 (`mentor_support` 4, «Иногда все еще приходится ждать ответа по сложным задачам»), СТ-003 п.5 (`task_clarity` 4, «По новым задачам иногда нужны дополнительные уточнения»).

**Без LLM:** фича выключается, числовые сигналы работают (требование ACCEPTANCE.md).

## 2. План разговора 1:1

**Боль:** HR видит красное, но не знает, с чего начать разговор. Стажёр боится, что его слова дойдут до наставника, который его оценивает.

**Выход** (расширяет `next_step`):

```json
{
  "situation": "1 фраза",
  "evidence_ids": ["..."],
  "questions": ["...", "...", "..."],
  "action_type": "weekly_1on1 | reduce_load | clarify_tasks | hr_talk | other",
  "mentor_message": "2–3 фразы, без цитат стажёра"
}
```

**Пример на СТ-005, период 1** (ориентир, не хардкод):
- основания: `task_clarity` 2 у стажёра против `task_understanding` 4 у наставника; `mentor_support` 2; «Не хватает регулярной обратной связи от наставника.»;
- действие: `weekly_1on1`;
- наставнику: «По итогам опроса предлагаем ввести короткие еженедельные встречи для сверки приоритетов по задачам».

**Без LLM:** шаблон `next_step` по `kind` сигнала.

## 3. Петля действий: «сделали → проверили»

**Боль:** если после анкеты ничего не меняется, в следующий раз стажёр ставит везде 4. Для HR-опросов это известная проблема: по данным Perceptyx 2026 (вендорское исследование), 71% сотрудников видят результаты опросов, но только 51% видят от них улучшения.

**Предлагаемая таблица** (согласовать с координатором):

```
actions: id, program_id, intern_id, period, action_type, comment, source, created_at
source ∈ {hr, history_comment}
```

**Поля, по которым считаем эффект** (period → period + 1):

| action_type | Поля |
|---|---|
| `weekly_1on1` | `mentor_support`, `task_clarity` (intern); `mentor_team_interaction` (mentor) |
| `reduce_load` | `workload_comfort` (intern); `deadline_organization` (mentor) |
| `clarify_tasks` | `task_clarity` (intern); `task_understanding` (mentor) |

**Предзаполнение истории.** `source = history_comment`, в UI подпись «восстановлено по комментарию анкеты»:

| Стажёр | Действие | Основание | Изменение в следующем периоде |
|---|---|---|---|
| СТ-003 | п.3 `weekly_1on1` | п.4, обе стороны: «После регулярных встреч…» | `mentor_support` 2→4, `task_clarity` 2→4, `overall_satisfaction` 2→4 |
| СТ-005 | п.3 `weekly_1on1` | п.4, обе стороны: «После регулярных встреч…» | `mentor_support` 2→4, `task_clarity` 3→4, `mentor_team_interaction` 3→4 |
| СТ-004 | п.4 `reduce_load` | п.5 наставник: «После снижения нагрузки…» | `workload_comfort` 2→4, `deadline_organization` 4→5 |

**Формулировка:** «в данных после действия показатели выросли», а не «действие дало эффект».

**API (предложение):** `POST /api/v1/actions`; в `GET /api/v1/interns/{id}` добавить `actions[]` с `effect`; в `GET /api/v1/overview` добавить `signals_without_action`.

## 4. Карта тем программы

**Боль:** HR разбирает каждого стажёра по отдельности и не видит, что проблема в устройстве программы.

**Логика:** матрица «тема × период», в ячейке число стажёров с негативным упоминанием темы с любой стороны. Данные берутся из разметки фичи 1.

**Ожидаемо на истории (размечено вручную):**
- `feedback`: п.1 — 3 из 5 (СТ-001, СТ-003, СТ-005), п.2 — 3, п.3 — 2–3, п.4 — 1, п.5–6 — 0;
- `clarity`: в основном СТ-003 и СТ-005 в п.1–3;
- `workload`: СТ-004 п.3–4, СТ-002 п.4.

**Вывод для HR:** обратная связь наставника — повторяющаяся тема первых трёх месяцев программы. Это повод обсудить регулярные 1:1 с первого месяца. Рекомендация, а не доказанный эффект.

## Промпт A: разметка комментария

```
Ты размечаешь комментарии из анкет стажировки МГТС. Верни только JSON.

Вход: {"response_id": "...", "source": "intern|mentor", "field": "...", "text": "..."}

Выход: {"response_id": "...", "items": [
  {"theme": "feedback|clarity|workload|planning|team|growth|none",
   "polarity": "negative|neutral|positive",
   "quote": "<дословная подстрока из text>"}
]}

Правила:
- feedback — нехватка обратной связи, ожидание ответа, редкие встречи с наставником.
- clarity — непонятные задачи, требования, приоритеты.
- workload — высокая нагрузка, много параллельных задач.
- planning — планирование, сроки, перенос сроков.
- team — сложности с командой.
- growth — желание более сложных или самостоятельных задач. Это НЕ жалоба: polarity = positive.
- «Сложностей нет», «ничего не мешает», «проблем нет» → none, neutral.
- В смешанной фразе размечай части отдельно.
- quote — строго дословный фрагмент text.
- Не делай выводов о состоянии человека («выгорание», «демотивирован»).
```

**Проверка в коде:** элемент, у которого `quote` не является подстрокой `text`, отбрасывается. На защите: «каждая цитата проверяется кодом на дословное совпадение, ИИ не может придумать основание».

## Промпт B: план разговора

```
Ты помогаешь HR стажерской программы МГТС подготовиться к разговору.
Верни только JSON по схеме: situation, evidence_ids, questions (3),
action_type, mentor_message.

Вход: стажер, период, сигналы с evidence_id (поле, значения, цитаты),
комментарии обеих сторон с response_id.

Правила:
- Ссылайся только на evidence_id из входа. Ничего не додумывай.
- Вопросы открытые, про ситуацию и задачи, без оценки личности.
- Без диагнозов и ярлыков.
- mentor_message: нейтрально, как предложение по формату работы.
  Не цитируй стажера и не пересказывай его слова.
```
