# Две внешние формы и автоматический прием

Реализован адаптер [Tally Webhooks](https://tally.so/help/webhooks): `POST /api/v1/integrations/tally`. После настройки Tally сам отправляет новые ответы. AI обрабатывается в очереди и не задерживает прием webhook.

## Настройка

1. Создайте две формы в своем аккаунте Tally: пульс-опрос стажера и оценка наставника. Вопросы и опорные шкалы — `questionnaires.md`; точные подписи — `web/questions.json` и таблица ниже.
2. Используйте **Short answer / Long answer** для строк, **Number / Rating** для оценок и месяца. Dropdown/multiple choice передают ID опций и этим адаптером намеренно отклоняются. Числовой месяц — 1–6; также допустима текстовая строка `Месяц 4`.
3. Опубликуйте обе формы. Укажите ID в `TALLY_INTERN_FORM_ID`, `TALLY_MENTOR_FORM_ID`, их URL — в `INTERN_FORM_URL`, `MENTOR_FORM_URL`. ID форм должны отличаться.
4. Настройте собственный публичный HTTPS reverse proxy до Go. В Integrations → Webhooks каждой формы укажите `https://<ваш-домен>/api/v1/integrations/tally` и один и тот же signing secret длиной не менее 24 символов. Сохраните этот секрет в `TALLY_SIGNING_SECRET`. Секрет не передается в URL и не включается в Git.
5. Перезапустите Go. Никаких карточек вручную создавать не нужно: используйте новый ID, например СТ-006 / IT, и Н-006 в анкете наставника. Все периоды пяти исходных участников уже заняты; новые ответы для них не должны перезаписывать историю.
6. Заполните обе внешние формы для СТ-006 и месяца 1. В HR → «Интеграции» должны появиться две доставки `accepted`, в профиле — обе анкеты. Повторная доставка того же события даст `duplicate` без новой записи. Проверьте новый статус и состояние очереди анализа.

Не считайте интеграцию подключенной до шага 6. В поставке проверены подписанные тестовые HTTP-запросы, а не отправка из аккаунта Tally. Реальные формы и публичный сервер требуют отдельной настройки владельцем аккаунта. В корпоративном пилоте выбор сервиса форм и внешней модели нужно согласовать с владельцем данных; транспортный контракт допускает внутренний сервис вместо Tally.

## Поля

| Общие поля | Тип |
|---|---|
| ID стажера | Short answer |
| Подразделение / направление стажировки | Short answer, точное совпадение с реестром |
| Контрольный период | Number, 1–6 |
| ID наставника | Short answer, только анкета наставника |

Подписи количественных и текстовых полей должны **точно** соответствовать названиям показателей из `questionnaires.md`. Названия в первой колонке таблиц, а не формулировки вопросов, служат label Tally. Формулировку вопроса и шкалу разместите в description.

После первого валидного webhook новый стажер регистрируется автоматически в одной транзакции с ответом. Если сначала пришла анкета стажера, mentorId остается пустым; поздняя анкета наставника заполняет его. Обратный порядок также поддержан. Известный наставник/подразделение не заменяются: несовпадение дает 422. Неподписанный запрос или невалидные оценки не создают участника. HR-ручка регистрации удалена.

Все 7 показателей стажера / 6 показателей наставника должны присутствовать в webhook. Не заполненная оценка допустима как null. Два открытых вопроса каждой формы также должны присутствовать; пустой текст допустим. Формы не являются авторизацией: знание чужого ID не подтверждает личность. Для реальных данных нужен корпоративный сервис с аутентификацией либо проверенные индивидуальные приглашения; встроенные кабинеты уже проверяют роль и привязку.

Адаптер сопоставляет форму по formId, показатели — по label; не доверяет переданному source. Подпись `Tally-Signature` проверяется как Base64 HMAC-SHA256 исходного JSON-body. При преобразовании JSON прокси подпись перестанет совпадать. Не переписывайте тело запроса на прокси. Сохраняются исходные значения вопросов, но ссылки на PDF из Tally с access token не сохраняются.

## Универсальный webhook

`POST /api/v1/integrations/responses`, заголовок `Authorization: Bearer <WEBHOOK_SECRET>`, тело `Response` из `openapi.json`. Секрет не короче 24 символов. После сохранения ответ автоматически добавляет задание анализа и запись в журнал доставки. Это позволяет использовать российский или внутренний сервис форм через небольшой нормализующий адаптер.

```json
{
  "eventId": "external:test-001",
  "programId": "mgts-internship",
  "internId": "СТ-006",
  "department": "IT",
  "month": 1,
  "source": "intern",
  "scores": {"taskClarity": 4, "mentorSupport": 3, "workload": 2, "interest": 5, "development": 4, "teamwork": 4, "satisfaction": 3},
  "comments": {"difficulties": "Много параллельных задач", "barriers": "Нужна сверка приоритетов"}
}
```

201 — сохранено; 200 — точный повтор; 400 — некорректный JSON; 401 — подпись/секрет; 409 — измененный повтор или занятый слот; 422 — ошибка полей/реестра; 503 — интеграция не настроена. Повтор с другим eventId для того же слота запрещен. Для одинакового eventId сравниваются бизнес-поля, без receivedAt и raw; изменение транспортных метаданных не считается новым ответом.

Для local-only демонстрации запустите `scripts/demo_webhook.py` на отдельной демобазе; он отправляет анкеты нового СТ-DEMO, проверяет его автоматическое появление, повторяет подписанный Tally webhook дважды и сверяет обновленный дашборд. Этот тест не обращается к Tally и не доказывает доставку из внешней формы.

## Наблюдаемость

HR видит последние 50 доставок: eventId, время, источник, accepted/duplicate/conflict/rejected. Подписи и секреты в UI и логах не показываются. Неавторизованные запросы не пишутся в бизнес-журнал, чтобы не сохранять недоверенные данные. HTTP-логи содержат requestId, метод и длительность без тела, cookie и query string.

При недоступности сервиса источник повторяет доставку с прежним eventId. Tally предоставляет журнал и повторные доставки в настройках webhook; точный актуальный порядок повторов смотрите в его документации. Ошибки в полях требуют исправления отправителем; автоматически повторять их бесконечно не нужно.
